# AutoSolver 项目文档

## 1. 系统概述

AutoSolver 项目包含两条相互独立的运行链路：

| 链路 | 入口 | 用途 |
|---|---|---|
| 正式比赛求解器 | `solver.py` | 接收比赛输入并返回合法分配结果。 |
| v7 网页演示 | `web_agent_demo/server_v7.py` | 展示全天调度、双屏对比、决策过程和长期记忆。 |

网页演示不替代正式求解器。它的作用是把算法对照、决策依据、订单状态和运力状态放到一个可交互工作台中。

## 2. 当前架构

```text
server_v7.py
  -> day_replay_frontend_v7.py
  -> run_full_day_comparison()
  -> build_dispatch_workbench_payload()
  -> 浏览器五页工作台
```

| 模块 | 责任 |
|---|---|
| `web_agent_demo/server_v7.py` | 复用基础 HTTP 服务，启用 v7 首页、实时派单和运行时花名册接口。 |
| `web_agent_demo/day_replay_frontend_v7.py` | 构造页面数据并渲染双屏对比、决策过程、长期记忆、订单池和骑手运力。 |
| `web_agent_demo/day_simulation.py` | 在同一订单流上运行基线和 AutoSolver，生成全天对照合同。 |
| `web_agent_demo/dispatch_workbench_data.py` | 把仿真合同转换为页面需要的实体、决策、记忆和地图数据。 |
| `web_agent_demo/compare_engine.py` | 运行候选策略并形成可比较的评分结果。 |
| `web_agent_demo/memory_engine.py` | 管理经验召回、排序和效果反馈。 |
| `web_agent_demo/road_routing.py` | 提供路线缓存、路径和距离数据。 |
| `web_agent_demo/runtime_roster.py` | 保存演示中临时增加的订单和骑手。 |
| `autosolver/`、`autosolver_agent/` | 提供求解、评估、控制、回退和 Agent 能力。 |

## 3. 启动与页面生成

`server_v7.py` 启动时完成三件事：

1. 载入基础 HTTP 服务和既有 API。
2. 启用离线路网缓存；未命中时使用稳定回退路线，避免演示依赖临时网络请求。
3. 将首页渲染函数替换为 `day_replay_frontend_v7.render_day_replay_index()`。

首次请求首页时，v7 页面会生成全天调度数据：

1. `run_full_day_comparison()` 创建订单、商家、骑手和时间片。
2. 最近距离贪心和 AutoSolver 在同一份输入上分别运行。
3. `build_dispatch_workbench_payload()` 生成订单、骑手、决策轮、记忆、指标和地图锚点。
4. 页面把结果嵌入 HTML，并由浏览器按推演时钟逐步播放。

同一个 payload 被五个页面共同使用，因此订单编号、骑手编号、决策轮和时间状态可以相互核对。

## 4. 两套算法对照

### 4.1 最近距离贪心基线

基线算法优先选择当前取餐距离最近的骑手。它计算快、规则直观，适合作为最低复杂度的对照方案，但不会主动平衡后续负载、合单机会和超时风险。

### 4.2 AutoSolver Agent

AutoSolver 在可行性约束内综合比较时效、配送成本、超时风险、骑手负载和顺路合单机会。不同场景可以在贪心、成本优先、风险均衡、匹配、稀疏覆盖和最小费用流等候选之间选择。

### 4.3 公平对照条件

- 两套算法接收相同订单和骑手初始状态。
- 两套算法沿相同时间轴推进。
- 每轮对比使用相同的已释放订单集合。
- 页面只改变调度算法，不改变订单流来制造差异。

相关契约由 `tests/test_day_simulation_comparison.py` 验证。

## 5. 五个页面

| 页面 | 数据来源 | 主要作用 |
|---|---|---|
| 双屏对比 | 两套算法的全天运行结果 | 同步显示地图、同单结果、累计指标和趋势。 |
| 决策过程 | `workbench.decisions` | 展示触发、输入、候选、过滤、评分、动作和回写。 |
| 长期记忆 | `workbench.memory` | 展示记忆分层、画像、召回链、学习曲线和反馈。 |
| 订单池 | `workbench.entities.orders` | 展示当前时刻已经释放的订单和两套算法结果。 |
| 骑手运力 | `workbench.entities.riders` | 展示班次、在线状态、负载、任务链和区域覆盖。 |

页面默认顺序就是评委演示顺序：先双屏看结果，再看决策和记忆，最后核对订单与运力输入。

## 6. 决策过程

一轮决策的数据结构包含：

| 字段 | 含义 |
|---|---|
| `trigger_reason` | 本轮重新调度的原因。 |
| `input_orders` | 当前时刻已经释放、需要处理的订单。 |
| `candidate_riders` | 当前可参与本轮分配的骑手。 |
| `filtering_process` | 班次、容量、时间窗和可行性过滤。 |
| `scoring_process` | 时效、成本和风险评分。 |
| `final_actions` | 最终采纳的派单动作。 |
| `abandoned_actions` | 被放弃的基线或候选动作及原因。 |
| `round_result` | 本轮对比结果。 |
| `result_writeback` | 本轮写入长期记忆的反馈。 |

决策页按这些字段顺序显示，不把最终结果当作唯一证据。

## 7. 长期记忆

长期记忆按“召回、注入、决策、回写”闭环运行：

1. 根据时段、天气、区域压力、订单风险和骑手供给筛选相关经验。
2. 将相似经验注入当前策略比较。
3. 执行派单并记录实际结果。
4. 把有效经验、失败原因和置信度反馈写回记忆。

页面把记忆整理为四类：全局策略、骑手画像、商圈/需求画像和订单风险画像。冷启动轮次没有历史命中；随着时间推进，后续相似场景可以召回已有经验，并在结果反馈后调整置信度。

相关数据结构由 `tests/test_dispatch_workbench_data.py` 和 `tests/test_day_simulation_memory_evolution.py` 验证。

## 8. 时间与因果边界

v7 对订单可见性采用严格的推演时钟：

- 下单时间之前，订单不会出现在地图、订单池或决策输入中。
- 下单之后，订单先进入等待状态，再随决策轮进入派单和配送状态。
- 骑手是否可用由班次、当前位置、当前负载和任务链决定。
- 页面跳转不改变底层时间状态，五个页面看到的是同一个时刻。

演示中新增订单或骑手时，`runtime_roster.py` 会把生效时间限制在当前推演时刻之后。后台重算只影响未来决策，已经发生的派单结果保持不变。

## 9. 路线和离线运行

当前版本通过 `road_routing_patch.py` 统一路线事实源，并默认读取 `web_agent_demo/route_cache.json`。这样可以在评委机器上不依赖 Python 第三方包运行。

地图组件优先加载 Leaflet；外部地图资源不可用时，页面仍提供内置回退视图。核心调度、指标、决策和记忆数据不依赖地图瓦片才能生成。

环境要求：Python 3.10 或更高版本。

```bash
python3 web_agent_demo/server_v7.py --host 127.0.0.1 --port 8799
```

## 12. 版本边界

| 版本 | 定位 |
|---|---|
| `server_v7.py` + `day_replay_frontend_v7.py` | 当前最终演示版本。 |
| `server.py`、`server_v2.py` 至 `server_v6.py` | 历史服务版本。 |
| `day_replay_frontend.py`、`day_replay_frontend_v2.py` 至 `day_replay_frontend_v6.py` | 历史页面版本。 |

历史文件保留是为了记录迭代过程，不会参与当前 v7 首页渲染。

## 13. 评审边界

- 双屏页面中的等待时间、配送成本、超时单和趋势来自当前演示仿真。
- 页面数据用于解释两套调度策略的差异，不替代比赛官方评测结果。
- 正式比赛求解入口始终是 `solver.py`。
- 当前网页演示入口始终是 `web_agent_demo/server_v7.py`。
